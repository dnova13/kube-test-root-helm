# Terraform 적용 후 세팅 순서 (AWS를 다시 올릴 때)

> 2026-10-07. AWS를 전부 내린 뒤 다시 올릴 때의 **전체 순서와 명령**을 한 곳에 모은 문서다.
> `terraform apply`는 AWS 쪽(IAM, EKS, 노드, RDS, EFS, ECR)만 만든다. 그 뒤 **클러스터 안과 DB 안**을 채우는 수작업이 남는데, 이 문서의 3절 스크립트(`bootstrap.sh`)가 한 번에 하고, 4절은 같은 내용을 손으로 할 때의 명령이다.
> `bootstrap.sh`는 미리보기(조회)와 따옴표 조립만 검증했고, **`--execute`로 전체를 실행해 본 적은 아직 없다.** 수작업 명령(4절)은 2026-10-07에 실제로 같은 순서로 실행해 성공한 것이다.
> 내릴 때는 [../scripts/README.md](../scripts/README.md)(`teardown.sh`).

## 전체 흐름

```
0 준비 → 1 terraform apply → 2 이미지 push(ECR) → 3 bootstrap.sh (클러스터 안 + DB + 서비스) → 5 확인 → 6 이후(데이터 채우기)
```

| 단계 | 하는 일 | 걸리는 시간(예상) |
|---|---|---|
| 1 | `terraform apply` | 20~30분 (클러스터 10~20분, 노드 10분, RDS 5~10분) |
| 2 | 서비스 이미지를 ECR에 push (`jib`) | 서비스당 1~3분 |
| 3 | `bootstrap.sh --execute` | 15~20분 (Redis·Kafka 기동, 서비스 배포, ALB 생성 포함) |
| 5 | 확인 | 5분 |

## 0. 준비

| 확인 | 명령·내용 |
|---|---|
| 도구 | `aws`, `terraform`, `kubectl`, `helm`, Docker(이미지 push용), Java 21(`./gradlew jib`) |
| AWS 자격 증명 | `aws sts get-caller-identity` (IAM 사용자와 Access Key는 AWS를 내려도 남아 있다) |
| DB 덤프 | `terraform/data/sns-dump.sql`이 있고 끝 줄이 `-- Dump completed ...` |
| SMTP 보관 파일 | `part3-notification-batch/ses-smtp.secret.env` |
| 마스터 비밀번호 정하기 | 8~41자, 공백과 `/` `'` `"` `@` 불가. `terraform apply`와 DB 복원에 같은 값을 쓴다. **서비스 계정(`sns-server`)의 비밀번호(`mysql-secret`)와는 별개** |
| 옛 state 정리 | AWS를 `teardown.sh`로 내렸다면 `rm terraform/aws/terraform.tfstate*` 후 시작하는 것을 권장 (`teardown.sh`는 `terraform destroy`가 아니라 CLI로 지우므로 state가 낡는다) |

## 1. Terraform 적용

```bash
cd terraform/aws
cp terraform.tfvars.example terraform.tfvars       # 필요한 값만 채운다 (노드 수 등). 기본값으로도 된다
export TF_VAR_db_password='<마스터 비밀번호>'        # 파일에 쓰지 않는다. 이 터미널에서만 유효

terraform init
terraform plan                                      # 만들어질 것을 읽는다 (비용 없음)
terraform apply                                     # 직접 실행, yes 입력. 비용 발생
```

- 끝나면 `terraform output`에 `cluster_name`, `efs_file_system_id`, `rds_address`, `ecr_registry` 등이 나온다. `bootstrap.sh`가 이 값을 읽는다.
- 확인: `terraform plan`이 `No changes`면 apply가 끝난 것이다.
- **AWS로 가는 문자열(이름, 설명, 태그)에 한글을 쓰지 않는다.** 보안 그룹 설명에 한글을 써서 처음 apply가 실패한 적이 있다.

## 2. 서비스 이미지를 ECR에 push

ECR 저장소는 Terraform이 만들지만 **이미지는 비어 있다.** 이미지가 없으면 서비스 Pod가 `ImagePullBackOff`가 된다. (이전 저장소를 지우지 않고 import했다면 이미지가 남아 있어 이 단계를 건너뛴다.)

> **`bootstrap.sh`(3절)는 ECR에 이미지가 없으면 이 작업을 자동으로 한다**(0단계: ECR 로그인 → `jib` → 프런트 `push-react.sh`). 이 절은 **손으로 먼저 올리고 싶을 때**, 또는 자동 빌드가 막혔을 때(Docker 미실행, `jib` 오류 등) 쓴다. 자동 빌드를 끄려면 `./bootstrap.sh --execute --no-build`.

```bash
# ECR 로그인 (계정 ID는 terraform output ecr_registry 의 앞부분)
aws ecr get-login-password --region ap-northeast-2 \
  | docker login --username AWS --password-stdin "$(cd terraform/aws && terraform output -raw ecr_registry)"

# 각 서비스에서 이미지를 빌드해 push (build.gradle의 jib 설정과 sns-chart의 태그가 같아야 한다)
for d in part3-feed-server part3-user-server part3-image-server part3-timeline-sersver part3-notification-batch; do
  (cd "$d" && ./gradlew jib)            # 에러 시 ./gradlew --stop 후 재시도
done

# 프런트엔드 (직접 만든 React 이미지)
part3-frontend/scripts/push-react.sh    # sns-frontend:react-1.0.0
```

| 서비스 | 이미지 | 태그 (`sns-chart/values.yaml` 기준) |
|---|---|---|
| feed | `feed-server` | 0.0.7 |
| user | `user-server` | 0.0.7 |
| image | `image-server` | 0.0.4 |
| timeline | `timeline-server` | 0.0.1 |
| notification | `notification-batch` | 0.0.3 |
| frontend | `sns-frontend` | react-1.0.0 |

- 각 서비스 `build.gradle`의 ECR 주소(`<계정ID>.dkr.ecr...`)가 **지금 계정**과 같아야 한다. 계정이 바뀌었다면 `build.gradle`과 `sns-chart/values.yaml`의 `global.imageRegistry`를 새 계정으로 고친다.
- 확인: `aws ecr describe-images --repository-name feed-server --region ap-northeast-2`에 태그가 보인다. `bootstrap.sh`도 시작할 때 차트가 쓰는 태그가 ECR에 있는지 점검한다.

## 3. 자동으로 하기: `bootstrap.sh`

```bash
cd terraform/scripts
./bootstrap.sh                       # 미리보기 (기본). 실행할 명령만 출력하고 아무것도 만들지 않는다
./bootstrap.sh --execute             # 실제 실행. DB 복원 때 마스터 비밀번호를 물어본다
                                     #   (TF_VAR_db_password 가 설정되어 있으면 묻지 않고 그 값을 쓴다)
./bootstrap.sh --execute --only 4    # 한 단계만 (실패한 단계부터 다시 할 때)
```

| 단계 | 하는 일 |
|---|---|
| 0 | **ECR에 이미지가 없으면 빌드해서 push**: ECR 로그인 → 없는 서비스만 `./gradlew jib`(실패하면 `./gradlew --stop` 후 한 번 더) → 프런트 `push-react.sh`. 끝나면 다시 확인하고, 이후 5단계 배포에서 클러스터가 ECR에서 받아 간다 |
| 1 | `aws eks update-kubeconfig`로 `kubectl`을 새 클러스터에 연결, 노드 Ready 대기 |
| 2 | 네임스페이스 `infra`·`sns`, ExternalName `mariadb`(새 RDS 주소), StorageClass `efs-sc`(새 EFS ID) |
| 3 | Secret 3개, IngressClass `alb`, Redis와 Kafka(Helm), Pod Ready 대기 |
| 4 | RDS에 마스터(`admin`)로 접속해 `sns-server` 계정 생성 → 덤프 복원 → 서비스 계정으로 행 수 검증 |
| 5 | `helm upgrade --install sns ./sns-chart -n sns` |
| 6 | 서비스 헬스체크, ALB 주소와 외부 응답(200) 확인 |

- **시작 전 점검**: `terraform output` 값, 덤프, SMTP 파일. 하나라도 문제면 중단한다.
- **이미지(0단계)**: 차트가 쓰는 이미지(태그 포함)가 ECR에 없으면 **자동으로 빌드·push**한다. 필요한 것은 실행 중인 Docker Desktop과 Java 21이고, 시간은 서비스당 1~3분·프런트 몇 분이다. push 뒤에도 없으면(예: `build.gradle`의 `jib` 태그와 `sns-chart/values.yaml`의 태그가 다름) 중단한다. `--no-build`면 자동 빌드 없이 중단, `ALLOW_MISSING_IMAGES=1`이면 이미지 없이 진행(Pod가 `ImagePullBackOff`). 5단계 배포 직전에도 한 번 더 확인해서, 이미지가 없으면 배포하지 않는다. 이 단계만 다시 하려면 `./bootstrap.sh --execute --only 0`.
- **중단 조건**: 어느 명령이든 실패하면 바로 멈춘다(순서가 있는 작업이라 건너뛰지 않는다). 원인을 해결한 뒤 `--only <실패한 단계>`로 이어서 한다. 대부분의 명령은 여러 번 실행해도 안전하다(`apply`, 이미 있는 Helm 릴리스는 건너뜀).
- **DB 복원 안전장치**: 덤프에 `DROP TABLE`이 있어서 기존 데이터를 덮어쓰지 않도록 대상 RDS를 먼저 확인한다. `sns` DB가 없으면 복원하고, **이미 있고 데이터(`user` 행)가 있으면 "이미 복원됨"으로 보고 복원만 건너뛴 채 계속 진행**한다(그래서 스크립트를 처음부터 다시 실행해도 5, 6단계까지 간다). `sns` DB는 있는데 `user` 테이블이 비었거나 읽을 수 없으면 일부만 만들어진 상태일 수 있어 덮어쓰지 않고 중단한다. 서비스 계정(`sns-server`) 생성은 매번 확인한다(이미 있으면 그대로).
- **마스터 비밀번호 입력**: 프롬프트는 입력이 보이지 않아 **한글 입력 상태에서 영문을 치면 다른 글자가 들어가** 접속이 거부된 적이 있다. `TF_VAR_db_password='<비밀번호>' ./bootstrap.sh --execute`처럼 환경변수로 넘기면 입력을 거치지 않는다(`$`가 있으면 작은따옴표).
- 마스터 비밀번호는 임시 Secret(`dbadmin`)으로만 쓰고, 끝나면(실패해도) 임시 Pod와 함께 지운다. 화면에는 표시하지 않는다.

## 4. 손으로 하기 (bootstrap.sh의 각 단계와 같은 명령)

스크립트를 쓰지 않거나, 한 단계씩 확인하며 하고 싶을 때의 명령이다. 2026-10-07에 이 순서로 실행해 성공했다.

### 4-1. kubectl 연결

```bash
aws eks update-kubeconfig --region ap-northeast-2 --name sns-cluster
kubectl get nodes                                    # 노드 Ready
```

### 4-2. 네임스페이스, ExternalName(RDS), StorageClass(EFS)

```bash
cd terraform/aws
EFS=$(terraform output -raw efs_file_system_id)
RDS=$(terraform output -raw rds_address)
cd ../..

kubectl create namespace infra
kubectl create namespace sns

# 클러스터 안에서 RDS를 mariadb.infra.svc.cluster.local 이름으로 부르게 한다
kubectl apply -f - <<EOF
apiVersion: v1
kind: Service
metadata:
  name: mariadb
  namespace: infra
spec:
  type: ExternalName
  externalName: $RDS
EOF

# StorageClass: 저장소의 efs-sc.yaml 은 fileSystemId 가 자리표시자(fs-000...)라서 새 EFS ID로 바꿔 적용한다
sed -E "s/fileSystemId: .*/fileSystemId: $EFS/" part3-infra/efs-sc.yaml | kubectl apply -f -
kubectl get sc                                       # efs-sc
```

### 4-3. Secret 3개, IngressClass, Redis, Kafka

```bash
# Secret (sns 네임스페이스). mysql, kafka 는 저장소 YAML, email 은 보관 파일에서
kubectl apply -f part3-feed-server/mysql-secret.yaml
kubectl apply -f part3-feed-server/kafka-secert.yaml          # 파일명 오타(secert)는 저장소 그대로
kubectl -n sns create secret generic email-secret --from-env-file=part3-notification-batch/ses-smtp.secret.env

# IngressClass alb (클러스터 공용, Auto Mode가 이것을 보고 ALB를 만든다)
kubectl apply -f part3-infra/manifests/ingress-class.yaml

# Redis, Kafka (infra 네임스페이스). Kafka 비밀번호는 kafka-secret 의 KAFKA_PASSWORD 와 같아야 한다
helm -n infra install redis oci://registry-1.docker.io/bitnamicharts/redis \
  --set architecture=standalone --set auth.enabled=false --set master.persistence.enabled=false

KAFKA_PW=$(grep KAFKA_PASSWORD part3-feed-server/kafka-secert.yaml | awk '{print $2}' | base64 -d)
helm -n infra install kafka oci://registry-1.docker.io/bitnamicharts/kafka \
  --set controller.replicaCount=3 --set sasl.client.passwords="$KAFKA_PW" \
  --set controller.persistence.enabled=false --set broker.persistence.enabled=false \
  --set global.security.allowInsecureImages=true --set image.repository=bitnamilegacy/kafka

kubectl -n infra wait --for=condition=Ready pod/redis-master-0 --timeout=5m
kubectl -n infra wait --for=condition=Ready pod -l app.kubernetes.io/name=kafka --timeout=8m
```

- Kafka는 `bitnamilegacy` 이미지로 설치한다(`bitnami/kafka` 태그가 사라져 `ImagePullBackOff`가 났던 적이 있다).

### 4-4. RDS 복원: 서비스 계정 생성 + 덤프

**마스터(`admin`)로** 접속해서 한다. 새 RDS에는 마스터만 있고 서비스가 쓰는 `sns-server` 계정이 없으며, 덤프는 `sns` DB만 담고 계정 정보는 없다.

```bash
# 1) 마스터 비밀번호를 임시 Secret 으로 (화면에 안 보이게 입력)
read -rs DBADMIN_PW
kubectl -n sns create secret generic dbadmin --from-literal=DBADMIN_PW="$DBADMIN_PW"

# 2) 임시 Pod. RDS 접속 정보(MYSQL_HOST 등)와 두 비밀번호가 환경변수로 들어간다
kubectl -n sns run dbrestore --restart=Never --image=mariadb:11.8 --overrides='{"spec":{"containers":[{"name":"dbrestore","image":"mariadb:11.8","command":["sleep","1800"],"env":[{"name":"MYSQL_HOST","value":"mariadb.infra.svc.cluster.local"},{"name":"MYSQL_PORT","value":"3306"}],"envFrom":[{"secretRef":{"name":"mysql-secret"}},{"secretRef":{"name":"dbadmin"}}]}]}}'
kubectl -n sns wait --for=condition=Ready pod/dbrestore --timeout=3m

# 3) 대상 확인: 새(빈) RDS 이고 sns DB 가 없어야 한다. 있으면 복원하지 않는다 (덤프의 DROP TABLE 이 지운다)
kubectl -n sns exec dbrestore -- sh -c 'mariadb -h "$MYSQL_HOST" -P "$MYSQL_PORT" -u admin -p"$DBADMIN_PW" --skip-ssl-verify-server-cert -N -e "SHOW DATABASES"'

# 4) 서비스 계정 생성 + 권한 (part3-infra/ddl.sql 4~5행과 같은 내용. 비밀번호는 mysql-secret 의 값)
kubectl -n sns exec dbrestore -- sh -c 'mariadb -h "$MYSQL_HOST" -P "$MYSQL_PORT" -u admin -p"$DBADMIN_PW" --skip-ssl-verify-server-cert -e "CREATE USER IF NOT EXISTS \"sns-server\"@\"%\" IDENTIFIED BY \"$MYSQL_PASSWORD\"; GRANT ALL PRIVILEGES ON sns.* TO \"sns-server\"@\"%\"; FLUSH PRIVILEGES;"'

# 5) 덤프 복원 (로컬 파일을 표준 입력으로 전달)
kubectl -n sns exec -i dbrestore -- sh -c 'mariadb -h "$MYSQL_HOST" -P "$MYSQL_PORT" -u admin -p"$DBADMIN_PW" --skip-ssl-verify-server-cert' < terraform/data/sns-dump.sql

# 6) 검증: 서비스 계정으로 접속해 행 수 확인
kubectl -n sns exec dbrestore -- sh -c 'mariadb -h "$MYSQL_HOST" -P "$MYSQL_PORT" -u "$MYSQL_USER" -p"$MYSQL_PASSWORD" --skip-ssl-verify-server-cert sns -N -e "SELECT COUNT(*) FROM user; SELECT COUNT(*) FROM social_feed"'

# 7) 정리 (마스터 비밀번호가 든 임시 Secret 도 지운다)
kubectl -n sns delete pod dbrestore
kubectl -n sns delete secret dbadmin
```

- 덤프를 받은 시점의 행 수는 `DB_덤프_복원_방법.md`에 있다.
- **함정: 이 Pod에서 `mariadb` 명령은 항상 RDS로 접속한다.** Pod에 RDS용 `MYSQL_HOST`가 환경변수로 들어 있어서, 로컬 소켓(`-S`)을 지정해도 클라이언트가 RDS로 간다. 이 Pod에서 다른 서버에 복원을 시험하지 않는다.
- 자세한 배경과 검증 결과: [DB_덤프_복원_방법.md](DB_덤프_복원_방법.md).

### 4-5. 서비스 배포

```bash
helm upgrade --install sns ./sns-chart -n sns --wait --timeout 8m
kubectl -n sns get pods
```

- Deployment, Service, ConfigMap 4개, 이미지 볼륨(PVC), 알림 CronJob(멈춤), Ingress(ALB)가 한 번에 만들어진다.
- Pod 수와 이미지 태그는 `sns-chart/values.yaml`의 값이다. 사용법은 `Helm_배포_치트시트.md`.

## 5. 확인

```bash
# 서비스 헬스체크 (port-forward 없이)
for s in feed-service user-service image-service timeline-service; do
  echo "$s: $(kubectl get --raw /api/v1/namespaces/sns/services/$s:8080/proxy/healthcheck/ready)"
done

# ALB 주소 (생성까지 1~4분. 처음에는 응답이 없을 수 있다)
ADDR=$(kubectl -n sns get ingress sns-ingress -o jsonpath='{.status.loadBalancer.ingress[0].hostname}'); echo http://$ADDR
for p in / /api/feeds /api/timeline; do echo "$p -> $(curl -s -o /dev/null -m 10 -w '%{http_code}' http://$ADDR$p)"; done
```

| 기대 | |
|---|---|
| 헬스체크 4개 | `ready` |
| `/`, `/api/feeds`, `/api/timeline` | 200 |
| `GET /api/feeds` | 덤프의 피드 수 (2026-10-07 복원 때 1,003개) |
| `GET /api/timeline` | **`[]` (비어 있음, 정상)**. 아래 「이후」 참고 |

## 6. 이후: 복원해도 비어 있는 것

DB 덤프에는 DB 안의 데이터만 있다. 그래서 다시 올린 뒤 화면에는 이렇게 보인다.

| 비어 있는 것 | 이유 | 채우는 방법 |
|---|---|---|
| **Timeline(타임라인 화면)** | Timeline 서버는 Kafka로 받아 Redis에 쌓은 것만 읽는다. Redis·Kafka가 새로 만들어져 비어 있다. DB의 피드는 `GET /api/feeds`로는 보인다 | 새 피드를 작성하면 반영된다. 기존 피드를 보이게 하려면 DB의 피드를 Kafka로 다시 보내는 도구가 필요하다(아직 없음) |
| **이미지 파일** | 이미지는 EFS에 저장되고 DB에는 `imageId`만 있다. 새 EFS는 비어 있다 | 테스트 데이터 생성기로 이미지와 게시물을 새로 만든다 |

테스트 데이터 생성기(`part3-testdatagen`, Java 19+)로 새 사이트에 데이터와 이미지, 타임라인을 한 번에 채울 수 있다.

```bash
cd part3-testdatagen
# ALB 주소 하나로 세 서버(user/feed/image)를 지정하는 방식
SNS_DATA_GENERATOR_BASEURL=http://<ALB 주소> java -jar TestDataGen.jar 100
# 또는 Telepresence 로 클러스터 네트워크에 붙여서
telepresence connect
SNS_DATA_GENERATOR_TELEPRESENCE_ENABLED=true java -jar TestDataGen.jar 100
```

- 숫자는 만들 게시물 수다. 이미지 원본(`part3-testdatagen/image/`, 772장)은 이 PC에 있다(git 제외).
- 새로 만들면 복원한 DB의 데이터 **위에 추가**된다. 옵션과 이전 실행 결과는 `part3-testdatagen/TestDataGen_설명.md`.
- ALB 주소로 직접 실행하는 방식(`BASEURL`)은 이 환경에서 확인하지 못했다. 안 되면 Telepresence 방식을 쓴다.

## 7. 막혔던 곳 (처음 해 보며 겪은 것)

| 증상 | 원인·해결 |
|---|---|
| `terraform apply`에서 보안 그룹 생성 실패 (`Character sets beyond ASCII`) | 설명(description)에 한글. AWS로 가는 문자열은 영어로 |
| `RepositoryAlreadyExistsException` (ECR) | 이전 저장소가 남아 있었다. 지우거나 `terraform import`로 가져온다(이미지가 보존됨) |
| 복원 때 `Access denied for user 'sns-server'` | 새 RDS에는 마스터(`admin`)만 있다. 마스터로 `sns-server`를 먼저 만든다(4-4) |
| 마스터로도 `Access denied` | `terraform apply` 때 넣은 비밀번호와 다른 값을 쓴 것. 같은 값을 넣는다 |
| 이 Pod에서 로컬 소켓 복원 시험이 RDS로 접속 | `MYSQL_HOST` 환경변수 때문. 위 4-4의 함정 |
| 사이트에 이미지와 타임라인이 비어 있음 | 6절 |
| ALB 접속이 `000` | 생성 중. 1~4분 뒤 다시 |

## 8. 비용과 내릴 때

- 켜 두는 동안 EKS 클러스터, 노드 3대, ALB, RDS, EFS가 과금된다. 쓰지 않으면 바로 내린다.
- 내릴 때: `terraform/scripts/teardown.sh` (미리보기 → `--execute`). 지우기 전에 **새로 쌓인 DB 데이터가 있으면 덤프를 다시 받는다**(`DB_덤프_복원_방법.md` 3절).
- Terraform으로만 내리려면 `helm uninstall sns -n sns`(ALB 먼저) 후 `terraform destroy -var db_password=unused`. `destroy`만 하면 클러스터가 만든 ALB가 남아 과금이 계속되고, 옛 환경 잔여물도 지워지지 않는다. 자세한 내용은 [../README.md](../README.md)의 「Terraform으로만 내리기」.
- 시작 전 준비물(덤프, SMTP 보관 파일, IAM 사용자 Access Key)은 AWS를 내려도 남아 있으니 지우지 않는다.
