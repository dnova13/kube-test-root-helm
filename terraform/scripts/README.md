# teardown.sh 사용법

> 2026-10-07 개정. AWS에 떠 있는 **sns 실습 환경을 전부 내려 과금을 멈추는 스크립트**다. `terraform destroy`는 쓰지 않고 **AWS CLI로 이름을 지정해 지운다.**
> Terraform으로 만든 환경(`sns-cluster` 등)과 수작업으로 만든 옛 환경(`test-cluster`, 옛 IAM Role, 옛 EFS 등)을 모두 지운다. 다시 올릴 때는 `terraform apply`([../README.md](../README.md)).
> **미리보기(조회)만 실행해 봤고, `--execute`로 실제 삭제는 이 버전으로 해 본 적이 없다.** 이전 버전(옛 환경 기준)으로는 일부 단계가 실제로 실행된 적이 있다.

## 1. 빠른 사용

```bash
cd terraform/scripts

./teardown.sh                  # 1) 미리보기 (기본). 지울 대상과 실행할 명령만 출력하고 아무것도 지우지 않는다
./teardown.sh --execute        # 2) 전부 삭제. 시작 시 delete-all 을 직접 입력해야 한다
./teardown.sh --only 8         # 3) 점검만 (남은 리소스 조회). 언제 실행해도 안전하다
```

순서: **미리보기를 읽고 → `--execute` → 8단계 점검 결과 확인.** `--execute`에 `--only`를 붙이지 않으면 1~8단계를 모두 실행한다. 실행하면 화면 출력이 `scripts/logs/teardown-<시각>.log`에도 남는다(중간에 끊겨도 어디까지 됐는지 확인할 수 있다).

## 2. 단계 (의존성 역순)

| 단계 | 하는 일 | 대기 시간(예상) |
|---|---|---|
| 1 | 클러스터 안: Helm 릴리스 전부, 남은 Ingress(ALB)와 PVC 삭제 → ALB가 사라질 때까지 대기 | 수 분 |
| 2 | 노드 그룹 → EKS 클러스터 삭제 (`sns-cluster`, `test-cluster`. 애드온은 클러스터와 함께 사라짐) | 각 10~20분 |
| 3 | RDS `sns-db` 삭제 (최종 스냅샷 없음, 자동 백업도 삭제) | 수 분 |
| 4 | EFS 마운트 대상 삭제 → 파일 시스템 삭제 (`sns-efs-volume`, `efs-volume`) | 1~3분 |
| 5 | ECR 저장소 6개 삭제 (이미지 포함) | 즉시 |
| 6 | IAM Role 삭제(새 이름 `sns-eks-*` 등과 옛 이름 모두), 클러스터가 하나도 남지 않으면 EKS OIDC 공급자 삭제 | 즉시 |
| 7 | 전용 보안 그룹 `sns-data` 삭제, 기본 보안 그룹에 추가했던 옛 규칙(3306, 2049) 정리 | 즉시 |
| 8 | 남은 리소스 점검 (조회만) | 즉시 |

- **순서가 중요하다.** ALB가 남으면 VPC 쪽 삭제가 막히고, 노드 그룹이 남으면 클러스터 삭제가 거부되고, 보안 그룹은 RDS·EFS가 사라진 뒤에야 지워진다. 스크립트가 순서를 고정한다.
- 지우는 대상의 이름은 스크립트 위쪽 변수(`CLUSTERS`, `DB_IDS`, `EFS_NAMES`, `ECR_REPOS`, `IAM_ROLES`, `DATA_SG_NAME`)에 있다. 이름이 바뀌면 거기를 고친다.
- 한 단계만 따로 실행할 수도 있다(`--execute --only 4`). 단 6단계의 OIDC 공급자는 **클러스터가 모두 사라진 뒤**에만 지워지므로, 2단계가 끝난 뒤 실행한다. 미리보기에서는 클러스터가 아직 있어서 "OIDC는 지우지 않는다"고 보이는 것이 정상이다.

## 3. 실행 전 체크리스트

| 확인 | 이유 |
|---|---|
| `terraform/data/sns-dump.sql`이 끝까지 받아졌는지 | RDS를 지우면 데이터가 사라진다. 덤프가 없으면 `--execute`가 중단된다 |
| `part3-notification-batch/ses-smtp.secret.env`가 있는지 | SMTP 계정은 클러스터 Secret에만 있고 이 파일이 보관본이다 |
| 루트 저장소의 변경을 커밋·push 했는지 | 로컬 파일은 지워지지 않지만, 백업 겸 안전하다 |
| 옛 EFS(`efs-volume`)의 이미지 파일이 필요한지 | 4단계가 지운다. 필요하면 지우기 전에 따로 백업한다 |
| AWS 자격 증명이 되는지 | `aws sts get-caller-identity` |

스크립트가 시작할 때 위 항목을 점검해서 문제가 있으면 `!`로 알려 준다. 덤프 문제는 중단하고, 나머지는 경고만 한다.

## 4. 지우지 않는 것

| 항목 | 이유 |
|---|---|
| **IAM 사용자와 Access Key** | Terraform·CLI 실행에 필요하다. 이 스크립트는 IAM 사용자를 건드리지 않는다 |
| SES 설정, SMTP용 IAM 사용자 | 알림 메일용. 스크립트 대상이 아니다 |
| 기본 VPC, 서브넷, 서브넷의 `kubernetes.io/role/elb` 태그 | 비용이 없고, 다시 올릴 때 Terraform이 같은 값을 쓴다 |
| 로컬 파일 | `terraform/data/sns-dump.sql`, `ses-smtp.secret.env`, 코드, 문서 등. 이 스크립트는 로컬 파일을 지우는 명령이 없다 |

## 5. 안전장치

- **기본은 미리보기**다. `--execute`를 줘야만 지운다.
- `--execute`는 시작 전에 **`delete-all`을 직접 입력**해야 진행한다.
- **덤프가 없거나 끝까지 받지 못했으면 중단**한다(`ALLOW_NO_DUMP=1`로만 강제).
- 클러스터마다 **임시 kubeconfig**를 만들어 쓰므로 `~/.kube/config`의 현재 컨텍스트가 바뀌지 않고, 다른 클러스터를 지울 위험도 없다.
- ALB가 남아 있으면 다음 단계로 넘어가지 않고 중단한다.
- **이미 없는 리소스는 건너뛴다.** 중간에 멈췄을 때 같은 명령을 다시 실행해도 된다.
- 한 명령이 실패하면 `! 실패(...)`를 남기고 **다음 명령으로 계속 간다.** 끝난 뒤 8단계 점검을 꼭 본다.

## 6. 다시 올릴 때: Terraform state가 낡는다

이 스크립트는 `terraform destroy`가 아니라 CLI로 지우므로, `terraform/aws/terraform.tfstate`는 **이미 없어진 리소스를 기억**한 채로 남는다. 다시 올릴 때 둘 중 하나로 한다.

- **권장: state를 지우고 새로 시작** — `rm terraform/aws/terraform.tfstate*` 후 `terraform apply`. 깔끔하게 전부 새로 만든다. 이 파일은 git에 올라가지 않는다.
- 지우지 않고 `terraform apply`만 해도 Terraform이 없어진 것을 감지해 다시 만든다. 다만 ECR처럼 state에 import 기록이 남아 있으면 `plan`에서 의도와 다른 변경이 보일 수 있으니 `plan`을 먼저 읽는다.

## 7. 끝난 뒤 확인

8단계가 아래를 조회한다. **모두 비어 있어야 과금이 없다.**

| 항목 | 남아 있으면 |
|---|---|
| EKS 클러스터, RDS 인스턴스, EFS, ECR 저장소 | 해당 단계를 다시 실행하거나 콘솔에서 삭제 |
| 로드밸런서(ALB/NLB) | 콘솔(EC2 > 로드밸런서)에서 삭제 |
| 사용 안 하는 EBS 볼륨, ENI, 미연결 탄력적 IP, NAT 게이트웨이 | 콘솔에서 삭제 (ENI는 ALB·EFS 삭제 후 몇 분 뒤 사라진다) |
| 실행 중인 EC2 | 노드가 남은 것. 클러스터·노드 그룹 삭제가 끝났는지 확인 |
| EKS OIDC 공급자 | 클러스터가 없는데 남아 있으면 6단계를 다시 실행 |
| 전용 보안 그룹 `sns-data` | RDS·EFS 삭제가 끝난 뒤 7단계를 다시 실행 |
| RDS 수동 스냅샷 | 이 스크립트는 만들지 않는다. 직접 만든 것이면 필요 없을 때 삭제 |

마지막에 **AWS Billing 대시보드**에서 과금 항목이 없는지도 확인한다(반영에는 하루쯤 걸린다).

## 8. 문제가 생겼을 때

| 증상 | 원인·조치 |
|---|---|
| 1단계에서 `helm uninstall`이 오래 걸리거나 시간 초과 | `--wait --timeout 5m`이다. 다음으로 넘어간다. 끝난 뒤 `./teardown.sh --execute --only 1`을 다시 실행 |
| `ALB가 남아 있어 중단합니다` | 콘솔에서 `k8s-`로 시작하는 로드밸런서를 확인·삭제한 뒤 다시 실행 |
| 2단계에서 `delete-cluster`가 노드 그룹 때문에 거부 | 노드 그룹 삭제가 아직 안 끝난 것. 상태를 보고 `--only 2` 다시 실행 |
| 3단계에서 `DeletionProtection` 오류 | `aws rds modify-db-instance --db-instance-identifier sns-db --no-deletion-protection --apply-immediately` 후 다시 실행 |
| 4단계에서 `FileSystemInUse` | 마운트 대상 삭제가 아직 안 끝난 것. 잠시 뒤 `--only 4` 다시 실행 |
| 6단계에서 `DeleteConflict` (Role 삭제 실패) | 정책이 붙어 있거나 인스턴스 프로파일이 연결된 것. 메시지의 이유를 확인하고 해당 Role만 콘솔에서 정리 |
| 7단계에서 `DependencyViolation` (보안 그룹 삭제 실패) | RDS·EFS의 네트워크 인터페이스가 아직 남은 것. 몇 분 뒤 `--only 7` 다시 실행 |
| 중간에 터미널이 끊겼다 | 같은 명령을 다시 실행한다. 이미 지운 것은 건너뛴다. `scripts/logs/`의 로그로 어디까지 됐는지 확인 |

위 표는 AWS CLI와 EKS·RDS·EFS의 일반적인 동작에서 정리한 것이고, 이 버전으로 실제 삭제를 하며 겪은 오류가 아니다. 실제로 실행하면서 다른 오류가 나오면 이 표를 고친다.

## 9. 알려진 한계

- 이 버전의 실제 삭제(`--execute`)는 아직 검증하지 못했다. 미리보기에서는 지울 대상이 의도와 일치하는 것만 확인했다(EKS 클러스터와 노드 그룹, RDS, EFS 2개, ECR 6개, IAM Role 8개, 전용 보안 그룹, 보안 그룹 규칙 3개).
- Kubernetes가 만든 EBS 볼륨이나 ENI는 클러스터 삭제 뒤에도 남을 수 있어 8단계 점검이 필요하다.
- 이 스크립트는 `sns` 실습 환경 전용이다. 이름이 고정되어 있어 다른 계정·클러스터에는 그대로 쓰지 않는다.
- 이 스크립트는 **새 환경과 이름이 같은 RDS(`sns-db`)와 ECR을 구분 없이 지운다.** 지금 떠 있는 환경을 전부 내리려는 목적에 맞춘 것이므로, 일부만 남기려면 `--only`로 단계를 고른다.
